Deploying Applications Notebook — Design Spec

Date: 2026-04-16 Course: PRG 400: Advanced Python Output: prg400/DeployingApplications.ipynb

Goal

Teach PRG 400 students the full deployment stack for a Python web application — from REST API fundamentals through FastAPI, SQLite, Docker, Docker Compose, Nginx, and DNS. Students leave with a clear mental model of how a request travels from a browser to a database, and how to containerize and serve their own application.

Running Example

A Task Manager API (tasks) — a minimal REST API that lets users create, list, and complete tasks. Simple enough not to distract from deployment concepts; real enough to demonstrate every layer of the stack.

Domain: http://tasks.example.com (used in DNS section)

Approach

Copy-paste notebook: Code cells contain example code for students to copy and run in their own environment. No auto-executing file writers. Docker/Nginx cells show config files and terminal commands — students follow along in their terminal. FastAPI sections can be run directly with uvicorn from the terminal.

Matches PRG 400 style: rich markdown, ASCII diagrams, tables, <details> solution blocks for the challenge.

Sections

Section 0 — What We're Building

  • Final architecture diagram showing the full request path
  • Overview of every layer: Browser → DNS → Nginx → FastAPI → SQLite
  • Brief explanation of what each component does
  • What students will have by the end

Section 1 — REST APIs & HTTP

Concepts only (markdown): - What an API is; what REST means - The HTTP request/response model - HTTP methods: GET, POST, PUT, PATCH, DELETE — what each is for - HTTP status codes: 200, 201, 400, 404, 422, 500 - Request anatomy: method, URL, headers, body - Response anatomy: status, headers, JSON body - Table: REST conventions (method + path → meaning)

Section 2 — Browser Clients & Consuming APIs

Concepts only (markdown): - What a "client" is (browser, mobile app, curl, another server) - How a browser makes an HTTP request when you type a URL - The browser's role vs the API's role - Brief JavaScript fetch example (conceptual — shows what the browser sends) - Tools for testing APIs: curl, Postman, Swagger UI (built into FastAPI)

Section 3 — FastAPI — First Endpoint

Code cells (copy-paste, run with uvicorn): - What FastAPI is; why it's used (automatic docs, Pydantic validation, speed) - Install: pip install fastapi uvicorn - main.py v1: in-memory task list, GET /tasks, POST /tasks, PATCH /tasks/{id}/complete - Pydantic models: TaskCreate, TaskResponse - Running: uvicorn main:app --reload - Visiting http://localhost:8000/docs — Swagger UI walkthrough - Testing with curl examples

Section 4 — SQLite Database

Code cells (copy-paste): - What SQLite is; why it fits small/medium apps and local dev - SQLAlchemy setup: database.py — engine, session, Base - ORM model: Task table (id, title, completed, created_at) - Updated main.py v2: replaces in-memory list with DB calls - CRUD operations wired through SQLAlchemy session - GET /tasks, POST /tasks, PATCH /tasks/{id}/complete — now persistent - Viewing the SQLite file: sqlite3 tasks.db

Section 5 — Docker

Code cells (Dockerfile + shell commands): - What a container is vs a virtual machine (table comparison) - Why containers matter for deployment: "works on my machine" problem - Dockerfile for the FastAPI app (multi-stage: builder + runtime) - Key Dockerfile instructions: FROM, WORKDIR, COPY, RUN, ENV, EXPOSE, CMD - requirements.txt contents - Build command: docker build -t taskapi . - Run command: docker run -p 8000:8000 taskapi - Useful Docker commands: ps, logs, exec, stop

Section 6 — Docker Compose

Code cells (docker-compose.yml + shell commands): - What Docker Compose is: orchestrating multiple containers together - Why use it: services, networking, volumes defined in one file - docker-compose.yml v1: single app service (FastAPI) - Key fields: build, ports, volumes, environment, depends_on - SQLite volume mount (persist DB outside container) - Commands: docker compose up --build, docker compose down, docker compose logs

Section 7 — Nginx as Reverse Proxy

Code cells (nginx.conf + updated docker-compose.yml): - What a reverse proxy is and why it's used - Nginx vs uvicorn: what each handles (serving static, SSL termination, routing vs Python execution) - ASCII diagram: Browser → Nginx :80 → FastAPI :8000 - nginx.conf: minimal reverse proxy config (upstream, server, location /) - Updated docker-compose.yml v2: adds nginx service, links to app - How Nginx and FastAPI communicate on the Docker internal network - Testing: curl http://localhost (port 80, through Nginx)

Section 8 — Putting It All Together

Summary + final complete file set: - Complete project structure (file tree) - Final main.py, database.py, Dockerfile, docker-compose.yml, nginx.conf - Step-by-step: how to bring the full stack up from scratch - Request trace walkthrough: what happens when curl http://localhost/tasks is run - Table: which component is responsible for what

Section 9 — DNS & Domain Names

Concepts + code (markdown + example zone file snippet): - What DNS is: the internet's phone book - How name resolution works step by step (recursive lookup diagram) - Browser cache → OS cache → Recursive resolver → Root NS → TLD NS → Authoritative NS - What an A record is: tasks.example.com → 203.0.113.42 - Other common records: CNAME, MX, TXT (brief table — context only) - How to point a domain to a server: registrar → DNS provider → add A record - How this connects to Nginx: once the domain resolves to the server IP, Nginx receives the request on port 80 - Example: what a DNS zone file entry looks like - Note on TTL: what it means and why it matters when changing records

Section 10 — Challenge

  • Students add a DELETE /tasks/{id} endpoint
  • Update the app, rebuild the Docker image, bring the stack back up
  • Verify with curl
  • Solution in <details> block

├── nginx/
│   └── nginx.conf       # Reverse proxy config
├── Dockerfile
├── docker-compose.yml
└── requirements.txt

Style Constraints

  • Matches existing PRG 400 notebooks: markdown-heavy, ASCII diagrams, tables
  • No emojis
  • Code cells: copy-paste, no auto-execution side effects
  • Shell commands shown as code blocks with bash syntax highlighting
  • Challenge uses <details> for the solution
  • No PostgreSQL — SQLite only (simpler for the deployment lesson)
